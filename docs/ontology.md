# Auto Ontology integration status

The independent PostgreSQL snapshot is implemented; the Auto Ontology semantic model and live MCP acceptance are **not yet verified**. The upstream repository was inspected at [d7e553e4c18112479c78b8f846e9929c4b5ed0a3](https://github.com/NVIDIA/auto-ontology/tree/d7e553e4c18112479c78b8f846e9929c4b5ed0a3) ([MCP guide](https://github.com/NVIDIA/auto-ontology/blob/d7e553e4c18112479c78b8f846e9929c4b5ed0a3/docs/mcp.md)). Upstream quickstart requires a configured model endpoint/key and an initialized deployment; its MCP server requires an authorized Auto Ontology API and OAuth session. No model credential or authenticated deployment is configured for this run. Do not present the SQL results below as an MCP or semantic-model result.

`integration/schema.sql` defines snapshots of review events, current non-superseded reviews, precomputed audit results and exclusions. `tools/postgres_export.py` copies only these facts from a local workspace using one transaction; it never reads reference corrections. It truncates the dedicated `avtriage` schema's snapshot tables: use a dedicated database and do not point at a shared production destination. Install `psycopg[binary]` separately, provision PostgreSQL and run:

```sh
PYTHONPATH=. python tools/postgres_export.py --workspace WORKSPACE --dsn "$AVTRIAGE_POSTGRES_DSN"
psql "$AVTRIAGE_POSTGRES_DSN" -f integration/golden.sql
```

Suggested ontology terms: release -> `release_id`, labeling policy -> `policy_id`, reopened image -> unique `image_id` in `reopened`, exclusions -> `policy_exclusions` with `evidence_id`, audit run -> `audit_results.design_id`; fractions and bounds are certified precomputed outputs, not language-model calculations. Include release, policy, population, sample, status and evidence in any answer. The current snapshot lacks vendor provenance, so “Which vendor caused this?” is unsupported. These are proposed mappings, not imported NVIDIA definitions.

An optional client, `tools/ontology_mcp_check.py --mcp-url URL`, uses the upstream `check_readiness` and `ask_question` MCP tools and compares typed rows with `integration/mcp_expected.json`. Install the `mcp` SDK separately and provide an MCP endpoint with a working authorized session/proxy. Fixture transport tests use a fake session and do not prove upstream connectivity. The local vendor-causation guard returns unsupported without asking a model. The suggested model mapping above is not yet an imported or validated Ossie file.

`integration/auto-ontology.yml` is a generated native model definition for the three read views; `integration/ossie.yml` is its Apache Ossie conversion. On 2026-11-19 the pinned upstream converter (`apache/ossie-converters` commit `cb4b46b97bcdb9f2685ef2f7023b9134a4426da2`, the revision required by the pinned Auto Ontology checkout) converted native YAML to Ossie and back successfully; all three datasets appeared. Regenerate native definitions with `python tools/ontology_definitions.py > integration/auto-ontology.yml`. Validation is an offline conversion, not a live import or evidence of successful semantic query. The native database name `triage` must be configured to the target dedicated database.

`integration/schema.sql` also defines `reopened_summary`, a certified distinct image count with evidence IDs grouped by release and policy. The native/Ossie definitions now include this view and an explicit event-to-exclusion join on event ID. Audit outputs are already computed and scoped by release, policy and run; no cross-run join is inferred. Rebuild an isolated synthetic snapshot and check all three SQL results with `PYTHONPATH=. python tools/ontology_fixture.py --dsn "$AVTRIAGE_POSTGRES_DSN"`; this replaces the dedicated schema's snapshot rows. The inputs are scripted fixture events, not human review.
